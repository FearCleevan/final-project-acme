## 4. Bot Filtering + User-Agent Storage on Pageview Analytics
User noticed a Vercel function log showing repeated 401s on `/api/admin/notifications` (explained as likely a second stale admin tab polling — a self-contained signed cookie session, not the same class of bug as the earlier OTP in-memory-Map issue) and a single unexplained `/legal/terms` hit, asking whether that meant a real customer was reading the legal page.

Investigated (no code changed until confirmed): found two entirely separate logging systems — Vercel's raw request logs (every HTTP hit, bots included, unfiltered) vs. the `page_views` Supabase table (only populated when a browser actually executes the client-side `PageViewTracker.tsx` JS). Found a real gap: `app/api/track/pageview/route.ts` had zero bot-signature detection and didn't retain the raw user-agent, so a JS-executing crawler (notably Googlebot, which runs JS for most crawls) would be indistinguishable from a real visitor in the analytics, with no way to check after the fact.

Fix (approved and built same session): a bot-signature regex (`bot|crawl|spider|slurp|facebookexternalhit|bingpreview|whatsapp|telegrambot|discordbot|pingdom|uptimerobot|headlesschrome`) now skips the database write entirely for matches — cheaper than before, not more expensive, since it's one less DB insert for bot traffic. Everything else now stores its raw `user_agent` (migration `015_pageview_user_agent.sql`) so an ambiguous visit can be checked directly instead of guessed at. No changes to `PageViewTracker.tsx` itself — storefront navigation/performance unaffected. Migration confirmed run successfully by user; code ready to commit/deploy.

## 5. Marketing Channel Research — Facebook Groups Rejected, Ads/Etsy Costs Gathered
User manually checked 3 Facebook "garage sale" style groups (Princeton BC, Whitehorse, Elk Valley Canada) as candidate marketing venues — all rejected. First two explicitly ban business advertising in their posted rules (one bans "advertising of small businesses" outright, the other bans anything resembling a "buy and sell" post/photo). Third (Elk Valley) technically allows "Home Based Businesses" but bans "Store Front Businesses" — genuinely ambiguous whether Acme (an established e-commerce brand, not a casual home seller) qualifies, recommended asking the group's admins directly rather than guessing. All three are also hyper-local, general audiences (one town/city each), not vintage/antique-collector communities — poor fit even where rules might allow it. Redirected toward legitimate channels instead: Meta/FB Ads (paid, sanctioned, avoids the whole "does this group allow it" problem), genuine antique/collector-specific groups (different category from garage-sale pages), organic content on Acme's own Page, Facebook Marketplace, and leveraging the SEO work already done.

Provided real cost figures for two of these: **Facebook/Meta Ads** — not free, budget-based (e.g. $5–10/day test), billed per impression/click. **Etsy** — $0.20 USD per listing (renews every 4 months if unsold, so ~$10 to list Acme's ~50 products initially), 6.5% transaction fee on sales, ~3%+fixed payment processing fee, optional Etsy Ads/Plus/Offsite Ads. Both framed as reasonable, numbers-driven asks for Scott rather than vague "can I get budget" requests — user was specifically worried that asking Scott for ad spend might undermine credibility; reframed as a normal e-commerce operating cost with a clear test-and-measure plan, not a sign of uncertainty.

Also reviewed a Google Images search showing Acme's own product photos dominating results for a specific long-tail product name ("Butterfly Beehive Shade Green 4\" Fit") — genuine organic SEO win. A follow-up broader search for just "oil lamp shade" showed Philippines-local Shopee/Lazada marketplace results instead (explained: geo-localized to the searcher's own location, and a generic 2-word term is inherently uncompetitive for a niche shop against mass marketplaces — not a real gap, long-tail specific terms are the correct/winnable SEO target for a business this size).

## 6. 51k Lead List (Brisk CRM) — Flagged, User Agreed Not to Use
User has 51,000 US/Canada leads obtained secondhand ("got it from someone I know, don't know how he got it") and initially wanted to send a throttled 50/day promotional blast to avoid spam filters. Clearly explained the distinction the user was missing: rate-limiting solves the *deliverability/spam-filter* problem, not the *consent* problem — CASL (Canada's Anti-Spam Legislation) applies regardless of send volume/speed, and an unverifiable-provenance list has no consent chain to point to if ever challenged. Also flagged the shared-sending-domain reputation risk, since the same Resend account/domain handles OTP and order-confirmation email, not just marketing. **User agreed not to use this list for Acme.** Recommended growing the real opted-in subscriber list (storefront signups) or legitimate paid channels instead. If this list resurfaces in a future session, the same concerns apply — don't build import/send tooling for it without the provenance question being re-resolved differently.
