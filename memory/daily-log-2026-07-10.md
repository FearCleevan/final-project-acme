## 3. Notification Bell — Scope Investigated, Upgrade Designed (Build Deferred)
Followed up on a gap flagged in [[daily-log-2026-07-09]]: only "new customer" triggers a bell notification, not Contact Inbox messages (e.g. Allan Jeffery's inquiry, now marked Replied).

**Root cause (not a bug):** `getAdminNotifications()` in `lib/admin/shopifyAdmin.ts` only ever reads Shopify (new orders 48h, low stock ≤3 units, new customers 7d) — never wired to Supabase, where Contact Inbox (`contact_messages`), Reviews (`reviews`), and Restock Waitlist (`back_in_stock_requests`) all actually live.

Ran full brainstorming-skill flow → design approved → spec written to `acme-lamp-sign/docs/superpowers/specs/2026-07-10-notification-bell-supabase-sources-design.md`. Adds 3 new notification types using the same isolated-try/catch-per-source pattern already used for the 3 Shopify sources:
- `contact_message` (unread `contact_messages`, severity `warning`, read-state comes free from existing `read_at` column/PATCH route — no new code needed for that part)
- `pending_review` (`reviews` where `status='pending'`, severity `info`, localStorage dismiss)
- `restock_signup` (`back_in_stock_requests` grouped by `product_handle` to avoid flooding the bell with one entry per signup, severity `info`, localStorage dismiss)

**User explicitly deferred the build to next shift** — not implemented yet, no code changed. writing-plans skill has NOT been invoked. Saved as the first entry in new [[pending-tasks-acme]] memory, which the user wants checked/updated every time they say "Acme Recap."
